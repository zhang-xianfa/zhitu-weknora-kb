# 07 · 业务优化路线：从"能答"到"敢用"

> 这篇不是功能清单，是把"企业为什么不敢用"拆成可执行的命题。
> 每一条都写了：现状 → 差距 → 这次落到了什么程度 → 怎么验收 → 还差什么。
> 已落地的部分在仓库里有代码、有单测、有可复跑的命令；没落地的部分明确标成路线图，不充数。

---

## 一、先承认一件事：POC 的死因通常不是"答不准"

Demo 阶段大家关心"它能不能答出来"，上线阶段业务方问的是另外四个问题，按被问到的频率排：

| 业务方的原话 | 背后真正的问题 | 技术上的名字 |
|---|---|---|
| "它答错了谁负责？我怎么知道它从哪抄的？" | 答案要能追到**源文件、版本、批次** | 可审计（provenance） |
| "这规定早改了，它还按老版本答？" | 库里同一制度有多个版本，检索没有"现在有效"的概念 | 时效治理（bitemporal） |
| "高管薪酬它也能答给普通员工？" | 检索只优化相关性，没做**权限过滤** | 访问控制（ACL） |
| "你们改完是变好还是变坏？谁签字？" | 没有**门禁**，改动全靠感觉 | 回归门禁（gate） |

再加一个很少被写进方案、但决定项目生死的：**一次问答多少钱、一次改动能多快验证**。

所以优化顺序不是"换更大的模型"，而是先把责任链和边界补齐。下面九条就是按这个顺序排的。

### 2.1 可审计：让"这条答案从哪来"能一句话答上来

**现状**：块只有 `doc_id + index`，重跑一次分块，index 全变；批次号只写在文档里，没有代码。

**做法**：

- `Chunk.uid` 是内容指纹（`doc_id + 层级路径 + 正文` 的 sha1 前 12 位）。内容没变，uid 就不变；
  改了两个字，uid 就变。跨批次对比时，"哪些块真的变了"不再靠猜。
- 批次台账一行一个文件：`batch_id / file / sha256 / mode / chunks / chunk_uids / chunks_detail / status / error`。
  `chunks_detail` 把"引用标题里的 `文档名#003`"映射回 uid 与条款路径，链条才是闭合的。
- 回溯链：用户反馈的答案 → 引用标题 `企业差旅与费用管理办法#003` → 台账 `chunks_detail[2]`
  → uid + 条款路径 → 源文件 sha256 + 入库批次与时间。

**验收**：

```bash
python -m pipeline.ledger --require-ok          # 上一批是否全部成功，失败退出码 3
```

**还差什么**：uid 只到块级，没有到"这句话"级；要精确到句子需要上游返回 span 偏移。
另外原样上传模式（`raw`）下引用标题由上游解析器决定，台账只能对到文件级——
想拿到条款级溯源，要用 `--mode chunks`。

### 2.2 时效治理：制度库必须有"现在有效"的概念

**现状**：V2.1 和 V3.2 都在库里，检索召回哪份算哪份，同一个人问两次可能得到两个答案。

**做法**（三条规则，都是制度管理的常识）：

1. 用**文件编号**归组：`HR-TR-2026-014` 是同一份制度的唯一锚点，没有编号才退化为标题；
2. **新版生效日 = 旧版失效日**。制度改版几乎没人给旧版补"失效日期"，如果只认显式失效，
   旧版会永远有效，每次体检都报"严重冲突"，告警打多了就没人看；
3. 支持 `--as-of`：回答"今年 1 月的时候标准是多少"这类历史问题，用同一个函数、同一个口径。

入库默认 `--version-policy latest`：同一制度只上当前有效的最新版，旧的记录原因后跳过；
`--version-policy keep` 保留全部（适合先做对比、暂不切换的场景）。

**验收**：

```bash
python -m pipeline.versioning --dir data/sample --as-of 2026-01-01
python -m pipeline.ingest --dir ... --dry-run --as-of 2026-01-01
```

**还差什么**：生效日期来自文档正文，填错就全错；真正可靠的做法是接文档管理系统/合同系统的主数据。

### 2.3 权限边界：相关 ≠ 该看

**现状**：零权限控制。通用 RAG 把召回的前 N 块直接拼进 prompt，等于默认"所有人能看所有制度"。

**做法**：

- 文档级密级（公开/内部/秘密/机密/绝密）+ 适用范围（部门）；
- 入库准入：文档密级高于知识库允许的最高密级时**拒绝入库**，逼着部署时把涉密制度拆到独立库、
  配独立 Token，而不是全塞进"全员制度库"；
- 检索后过滤：越权块在进 prompt 之前被摘掉；
- **越权话术 = 无答案话术**（`资料中没有找到相关内容。`）。"该文档存在但你没权限"这句话本身
  就是泄露；真实原因只进审计日志，日志里只记 `query_hash` 与文档 ID，不记问题原文和正文。

**验收**：

```bash
python -m pipeline.ingest --dir data/sample --dry-run --kb-clearance 公开   # 应当被阻断
python -m pipeline.security --chunks chunks.jsonl --clearance 内部           # 按角色看会漏出什么
```

**还差什么**：粒度只到文档级（与上游权限模型一致）；文档内部"部分条款更敏感"的情况需要拆文档。
**search 评测链路已经接上**：`pipeline.ingest --policies-out` 落策略清单，
`eval.runner --policies --clearance` 在检索后、评分前过滤，指标反映"这个角色真实能看到什么"。
`chat` 模式的上下文由问答服务拼装，需在问答服务侧对检索结果套同一份清单——
POC 内问答走 WeKnora，没有自建问答服务，这一侧留了接入点而不是假装已经接上。

### 2.4 文档体检：把工程问题还给内容问题

**现状**：答不准时，工程侧第一反应是调分块参数、换模型。但相当一部分根因在文档：
没标题、一条被拆成八行、附录重复三遍、表格贴成图片。

**做法**：入库前给每篇文档打分（0–100）并给**业务部门看得懂**的建议：

| 扣分项 | 权重 | 为什么扣 |
|---|---|---|
| 无标题块占比 | 40 | 短块没有层级路径，向量里几乎没有可检索语义 |
| 无条款路径占比 | 10 | 块不在任何条款下，引用无从谈起 |
| 裸短块（又短又没出处） | 25 | 召回噪声的主要来源 |
| 超限块占比 | 10 | 挤占上下文预算，排序易偏向大块 |
| 重复块占比 | 30 | 重复块挤掉真正不同的召回结果 |

**不扣分的两类**：开头的"【文档元信息】"块（流水线自己拼的，不是文档缺陷）、
一句话的条款（制度本来就会有一句话的条款，短不是罪，短且没出处才是）。

**验收**：

```bash
python -m pipeline.quality --dir data/sample --min-score 60     # 低于门槛退出码 3
```

**还差什么**：权重是经验值，不是学术指标；目前只对 Markdown/纯文本有效，docx 的结构问题读不出来。

### 2.5 回归门禁：把"看着还行"换成退出码

**现状**：`docs/03` 写了"命中率下降 > 5 个百分点视为回归失败"，但没有代码执行它。

**做法**：`eval/regression.py` 比较两份 `--summary-json`，按指标方向分别判：

| 方向 | 指标 | 门槛 |
|---|---|---|
| 越低越差 | 命中率 / 检索命中率 / 引用命中率 / 拒答率(负例) / 召回率@k / MRR | 允许下降 5 个百分点 |
| 越高越差 | 误拒率 / 含糊率 | 允许上升 5 个百分点 |
| 越长越差 | 延迟 P50 / P95 | 允许到基线的 1.5 / 2 倍 |

基线文件 `eval/baseline/offline.json` 进仓库。退化 → 退出码 1，发布流程必须解释或回滚。
CI 里用 `--ignore 本地检索P50_ms,本地检索P95_ms` 跳过噪声大的延迟指标，只卡正确性。

**验收**：

```bash
python -m eval.offline --chunks chunks.jsonl --cases eval/cases/enterprise_policy.json \
  --summary-json eval/report/offline.json
python -m eval.regression --baseline eval/baseline/offline.json --current eval/report/offline.json
```

**还差什么**：目前只卡离线召回基线；线上 chat 模式的 token 成本高，按发版频率跑，不进每次提交。

### 2.6 评测要能回答"是块没召回，还是标注写错了"

**现状**：只有一个"命中率"，下降时说不清是分块坏了、检索坏了，还是用例标注该改。

**做法**：把两层拆开：

- **召回层**：`expected_clause` 标注预期条款，算 `召回率@k` 与 `MRR`（排第 1 和第 3 差别很大）；
- **要点层**：`must_include` 关键词，严格判定"答全了没有"。

样例文档上的结果恰好说明了这个价值：**召回率@3 = 100%，MRR = 0.93，但严格命中率只有 87.5%**。
唯一没中的 `F-02`，块排在第 1 位，缺的只是"不需要"和原文"不需提供"差一个字。
——结论是"用例措辞该对齐"，不是"检索坏了"。没有分层，就只会看到"命中率掉了"，然后去乱调参数。

**还差什么**：`expected_clause` 要人工标；冷启动阶段只能先标高频问题。

### 2.7 badcase 回流：评测集要能长大

**现状**：种子用例是上线时手写的 12 条，之后没人维护；线上答错的问题散在聊天记录和工单里，
既没有进用例集，也没有进门禁。

**做法**：`eval/badcase.py` 把"反馈 → 用例"固化成流程，但**机器只整理、不判断**：

- 反馈（CSV/JSONL：question / answer / reason）→ 统一字段 → 按问题去重 → 候选 JSON；
- 同时生成 Markdown 复核表，带"这条原因通常意味着什么"的提示（例如"太慢"不该入集）；
- 人工补 `must_include` 或标 `unanswerable` 后，`--merge` 写回种子用例集；
- 合并门槛是硬的：正例没写考点直接拒绝，避免把噪声写进门禁。

**验收**：

```bash
python -m eval.badcase --feedback feedback.jsonl --cases eval/cases/enterprise_policy.json
python -m eval.badcase --feedback feedback.jsonl --cases eval/cases/enterprise_policy.json --merge
```

**还差什么**：反馈入口（前端"没解决"按钮、工单系统）还没接，目前靠人工导出 CSV/JSONL。

### 2.8 发布自检：把四道闸合成一条命令

**现状**：体检、版本、密级、指标各有各的 CLI，发布时没人愿意挨个跑四遍再人肉对结论。

**做法**：`ops/release.py` 一次扫描文档，输出可贴进发布单的四行清单，失败退出码 1：

```
[1/4] 文档体检   通过   1 篇，最低 100 分
[2/4] 版本时效   通过   1 份文档，无冲突
[3/4] 密级边界   通过   库密级 内部；角色 release-check/内部 可见 8/8 块
[4/4] 指标门禁   通过   召回率@3 1.000 / 命中率 0.875，无退化
结论：通过（0 项失败，0 项告警）
```

和 `ops.doctor` 的分工：doctor 查**线上服务**（连通/积压/空召回/延迟），release 查**离线资产**
（文档/版本/密级/指标），所以 release 能直接进 CI（`.github/workflows/ci.yml`）。

**验收**：

```bash
python -m ops.release --dir data/sample --ignore 本地检索P50_ms,本地检索P95_ms
```

### 2.9 数值题：别让模型读表硬算

**现状**：表格整表进一个块，解决了"看得见"，没解决"算得对"。
"出差 9 天谁审批"要做区间比较，"二线城市住 5 晚报多少"要做乘法——
语言模型做这两件事都不稳定，而错一次金额就是一次报销事故。

**做法**：同一张表走两条路。

| 路径 | 产物 | 用途 |
|---|---|---|
| 检索 | 整表入块 | 语义问答："审批权限怎么规定" |
| 结构化 | 表头/行/条款路径的 JSON | 数值题：等值/区间/包含查询 |

区间解析支持 `1-3 天`、`8 天及以上`、`3 天以内`、`500 元/晚`；
入库时 `--tables-out data/tables.json` 随批次导出，问答服务据此做数值旁路。

**验收**：

```bash
python -m pipeline.tables --dir data/sample --query "出差天数=9"
# [企业差旅与费用管理办法.md · 第二章 出差审批 › 第5条] 出差天数=8 天及以上，审批人=部门负责人 + 分管副总，...
```

**还差什么**：只处理 Markdown 表；合并单元格、多行表头、跨页续表不猜；
聚合与跨表 join 应该进数据库，不在这个 CLI 里做。

### 2.10 业务指标：命中率不等于"解决了"

**现状**：只有技术指标（召回/命中/延迟）。命中率 90% 的项目照样可能被判死，
因为用户点完"没解决"就转人工了——技术指标回答不了"省了几个人"。

**做法**：`ops/insights.py` 把交互日志算成业务方会看的数：

| 指标 | 口径（代理） | 对应动作 |
|---|---|---|
| 首次解决率 | 有用 + 未转人工 + 7 天内未重复问同一问题 | 低于 60% 不适合全量 |
| 转人工率 | 触发转人工的比例 | 高 → 看拒答率与含糊率 |
| 重复提问率 | 同一人窗口期内重复问同一问题 | 高 → 答案不可执行（缺流程/入口） |
| 引用点击率 | 点开引用核对的比例 | 低 → 引用位置没用或没人信 |
| 单次成本 | token × 单价 | 决定能否全员开放 |

并且把"没用/转人工/拒答"直接导出成 badcase 反馈，交给 `eval.badcase` 入集——
业务指标和评测集是同一个数据源，不用人工再导一遍。

**验收**：

```bash
python -m ops.insights --log data/interactions.example.jsonl \
  --price-in 0.002 --price-out 0.008 --monthly-volume 10000 \
  --export-feedback eval/report/feedback.jsonl
```

**还差什么**：真正接工单/转人工系统，才能算"真首次解决率"；目前靠行为信号近似，
评分覆盖率低时报告会直接提示"不可信"。前端埋点（有用/没用、引用点击）也要先补。

## 三、拒答分级：对用户只有一种"不知道"，对系统必须有四种

企业场景里"拒答"经常被当成一个动作，实际是四种完全不同的情况，处理错方向就是白干：

| 情形 | 系统内部判定 | 对外话术 | 运营动作 | 看哪个指标 |
|---|---|---|---|---|
| 库里确实没有 | 检索空 / 要点无支撑 | 资料中没有找到相关内容 | 补文档、补问答对 | 负例拒答率 |
| 有内容但证据不足 | 召回到但要点缺失/互相矛盾 | 资料中没有找到相关内容 | 改检索、补上下文、调 prompt | 含糊率 |
| 有内容但无权查看 | 权限过滤命中 | **同上，不说"无权限"** | 配权限、拆知识库 | 审计条数 |
| 服务不可用 | 熔断 / 5xx / 超时 | 知识库暂时不可用，请稍后再试 | 值班、降级 | 熔断次数、5xx 率 |

一条硬规则：**前三种对用户必须是同一个体验**，差异只进日志。否则用户能从话术差异
反推出"这条知识存在、只是我看不到"，权限设计就白做了。

代码里 `pipeline/security.py:UNAUTHORIZED_REFUSAL` 与"无答案"话术是同一个字符串，
`eval/metrics.py:classify_answer` 负责把模型输出分成 `refused / hedged / answered` 三档，
`含糊率` 单独进报告——因为它对应的动作（调 prompt/补上下文）和拒答率（补文档）相反。

## 四、技术指标会骗人，业务指标不会

命中率 90% 的项目照样可能被业务方判死，因为下面这些没人看：

| 业务指标 | 定义 | 为什么它更真实 |
|---|---|---|
| 首次解决率 | 一次问答后没有再问同一件事，也没有转人工 | 命中率只说明"答到了"，不说明"解决了" |
| 转人工率 | 点"没解决/转 HR"的比例 | 直接对应人力成本节省 |
| 引用点击率 | 用户点开引用核对的比例 | 越高说明越需要核对，也说明引用位置有用 |
| badcase 闭环天数 | 从用户反馈到用例入集、修复、验证的时长 | 衡量"这套体系有没有自我进化" |
| 单次问答成本 | (输入+输出 token × 单价) / 问答次数 | 决定能不能全员开放 |
| 无效提问占比 | 与制度无关的问题占比 | 决定要不要加意图拦截，省 token |

这些指标 POC 阶段采不到（没有真实用户），但**采集点现在就要留**：
问答接口返回 `trace_id`、引用列表、拒答类型；前端给"有用/没用"两个按钮。
不然后面想算也算不出来。

`ops/insights.py` 已经能按上面的口径算（代理指标），并把"没用/转人工/拒答"
导出成 badcase 反馈——缺的只是前端埋点与工单系统把数据喂进来。

## 五、组织与流程：知识库不是纯技术项目

| 角色 | 负责什么 | 不做的后果 |
|---|---|---|
| 业务部门（文档 owner） | 补标题、定密级、写生效日期、作废旧版 | 工程侧天天替他们改文档，改完还是答不准 |
| IT / AI（知识库 owner） | 分块规则、评测集、门禁、发布 | 没人对"答错"负责，出问题互相甩锅 |
| 安全/合规 | 密级标准、权限矩阵、审计留痕 | 涉密内容进公开库，合规事故 |

发布流程（也是 `docs/05` 变更规范的执行版）：

```
改分块/清洗/prompt
   → 离线基线（秒级，每次改都跑）
   → 回归门禁（退化即拦，退出码 1）
   → 样例库 chat 抽检（看拒答与引用）
   → 小流量（1~2 个部门）
   → 全量
```

一条容易被忽略的约定：**改分块参数必须全量重入库**。只对新增文档生效，库里会并存两套
切法，指标从此不可解释（`docs/05` 第 3 节）。

## 六、成本账：RAG 的成本几乎全在上下文

单次问答成本 ≈ `(检索块数 × 块长 + 问题 + 回答) × 单价`。三个杠杆：

1. **块数**：`match_count` 从 5 降到 3，input token 降约 40%，但召回率会掉——
   先用 `召回率@k` 看掉多少，再决定值不值；
2. **块长**：`max_chars` 600 是"一条制度 + 一张表"的经验值；切太碎块数变多，切太大噪声变多；
3. **模式**：search 模式评测几乎零成本（不调 LLM），chat 模式按发版频率跑。

`ops.insights --price-in/--price-out` 可以直接按交互日志算单次成本与月成本，
不用另做一张 Excel；单价按实际模型报价传，不要在代码里写死。

POC 阶段可以不算钱，但**方案里必须有一页成本估算**：知识库 200 篇、日均 200 次问答、
每次 4k input + 500 output，一个月多少钱。业务方批预算看的是这一页，不是命中率。

## 七、明确不做（以及为什么）

写"不做什么"比写"要做什么"更能说明想过：

| 不做 | 原因 |
|---|---|
| LLM 当裁判 | 裁判本身要评测，换个模型分数就变，企业侧没人愿意为不可复算的分数背书 |
| 条款级 ACL | 与 WeKnora 的库/条目级权限模型冲突；文档级已能挡住绝大多数事故 |
| 全自动表格计算 | "二线城市住 5 晚能报多少"需要结构化查询，让 LLM 硬算金额是错误的信任假设 |
| 多租户/计费 | 超出 POC 范围；单库 50~200 篇、并发 < 20 是当前边界 |
| 自动改文档 | 文档是业务资产，只能给建议清单，改动必须由 owner 做 |

## 八、路线图：三阶段，每阶段有明确的"退出门槛"

### 阶段 0：POC（当前）

- 单库、单部门、样例数据；离线基线 + chat 抽检；文档级密级；版本时效。
- **退出门槛**：20 个真实高频问题在样例库上召回率@3 ≥ 90%，负例拒答率 ≥ 80%。

### 阶段 1：试点（20~50 人，1~2 个部门）

- 接 SSO，拿真实部门/职级做 `Viewer`，不再手工传 `--clearance`；
- badcase 回流：前端"没解决"→ 落库 → 每周导出 → `eval.badcase` 生成复核表 → 补全入集
  （工具已就绪，差前端入口与每周例行）；
- 业务指标周报：`ops.insights` 按周出首次解决率/转人工率/重复提问率/单次成本，
  和门禁报告一起进群（没有这页，技术指标永远说服不了业务方）；
- 周度门禁：每周一跑一次 `ops.release` 全量基线，报告进群；
- 加"转人工"入口（HR/财务值班），统计首次解决率。
- **退出门槛**：首次解决率 ≥ 60%，转人工率 ≤ 30%，badcase 平均闭环 ≤ 7 天。

### 阶段 2：部门级（全公司制度库）

- 文档管理系统对接：生效/失效日期、密级、owner 从主数据来，不再从正文抽；
- 表格结构化：把权限矩阵、金额档位抽成结构化表，数值题走 SQL 而不是向量召回；
- 成本看板：token、缓存命中、单次成本；
- 版本灰度：新版本先"影子入库"，用历史问题对比新旧版本答案。
- **退出门槛**：单次问答成本可预算、审计可回溯到条款、密级事故为零。
