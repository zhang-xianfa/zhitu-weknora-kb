# 03 · 边界评测体系

## 一、为什么要专门做"边界"

企业知识库里，"答对常见问题"是最容易的部分——高频问题往往问法固定、文档里写得很直白。
真正让人不敢上线的，是下面这些：

- 文档里**根本没有**的内容，模型顺着上下文编了一个像样的答案；
- 两个版本的规定同时存在，模型混着答；
- 答案散在**两条不相邻的条款**里，只召回了一条；
- 文档里的表格写了，但被切碎了，答成了另一档。

所以用例按五类设计，其中**负例和时效类是这套体系的核心**。

## 二、用例结构

```json
{
  "id": "C-01",
  "category": "条款型",
  "question": "出差 9 天需要谁审批？",
  "must_include": ["分管副总"],
  "expected_source": "企业差旅与费用管理办法",
  "expected_clause": "第5条",
  "unanswerable": false
}
```

| 字段 | 用途 |
|---|---|
| `must_include` | 必答要点，**全部出现**才算命中（缺一即不命中，宁可严） |
| `expected_source` | 预期引用文档；为空表示该用例不考核引用 |
| `expected_clause` | 预期条款，用于算**召回率@k / MRR**；为空表示该用例不考核召回 |
| `unanswerable` | 负例标记；为 true 时不做要点比对，只看是否拒答 |

五类用例的数量配比（本仓库样例 12 条）：事实型 2、条款型 3、跨条款多跳 2、
无答案负例 3、时效与版本 2——其中时效类里"明年会调整吗"也是负例，
**合计 4 条负例，占 33%**。负例少于 20% 时指标会被乐观估计，所以这是硬要求。

## 三、指标口径

### 3.1 先分层：召回错，还是标注错？

只报一个"命中率"，指标掉了的时候没人说得清该改分块、改检索还是改用例。所以拆两层：

| 层 | 指标 | 定义 | 回答什么问题 |
|---|---|---|---|
| 召回 | **召回率@k** | 需考核召回的用例中，预期条款进入前 k 条的比例 | 块有没有被捞出来 |
| 召回 | **MRR** | 预期条款名次倒数的平均值 | 捞出来后排得靠不靠前 |
| 要点 | **命中率** | `must_include` 全部出现的比例 | 看到的块里有没有那句话 |
| 引用 | **引用命中率** | 引用里出现预期文档的比例 | 出处是不是真的 |
| 拒答 | **拒答率（负例）** | 负例被正确判为"资料中没有"的比例 | 会不会瞎答 |
| 拒答 | **误拒率 / 含糊率** | 有答案却拒答 / 给了倾向但没结论 | 拒答过头、和稀泥 |
| 性能 | **延迟 P50 / P95** | 端到端或检索耗时 | 能不能用 |

一个真实例子：样例库上 **召回率@3 = 100%、MRR = 0.93，但严格命中率只有 87.5%**。
唯一没中的 `F-02` 排在第 1 位，缺的只是"不需要"和原文"不需提供"差一个字。
两层指标把结论逼出来了：**该改用例措辞，不是检索坏了**。只有一个命中率时，你只会看到"掉了"。

### 3.2 回答分三档，不只有"答对/答错"

`eval/metrics.py:classify_answer` 把回答分成：

| 档 | 判定 | 含义 | 该做什么 |
|---|---|---|---|
| `refused` | 命中拒答措辞 | 库里确实没有 / 权限拦下 | 补文档、配权限 |
| `hedged` | 命中含糊措辞（"请以…为准""建议联系…"） | 有内容但不敢下结论 | 调 prompt、补上下文 |
| `answered` | 其他 | 给了明确结论 | 看要点是否命中 |

`refused` 和 `hedged` 的处理方向相反，混在一个"拒答"里，就等于没有指标。

### 为什么不用 LLM 当裁判

LLM 裁判自己也要被评测，企业侧没有人愿意为一个"换个模型就变"的分数背书。
本套指标刻意做得笨：关键词命中、条款路径命中、拒答措辞识别。
笨口径的好处是**任何人拿同一批数据都能算出同一个数**，适合做回归门禁。
主观质量（语气、完整度）另做小样本人工评分，不混进自动指标。

## 四、两种模式

| 模式 | 调什么接口 | 测什么 | 什么时候跑 |
|---|---|---|---|
| `search` | `/knowledge-search`（不调 LLM） | **召回**：资料有没有检索到 | 每次改清洗/分块/召回参数 |
| `chat` | `/knowledge-chat/{session}` | **端到端**：拒答、幻觉、引用 | 发版前、改 prompt/模型后 |

先看召回：召回不中，端到端一定不对；召回对了但端到端不对，问题在生成层。

## 五、怎么用

```bash
# 校验用例文件（不联网）
python -m eval.runner --cases eval/cases/enterprise_policy.json --dry-run

# 召回评测
python -m eval.runner --cases eval/cases/enterprise_policy.json --kb-id <id>

# 端到端
python -m eval.runner --cases ... --kb-id <id> --mode chat --session-id <sid>
```

产出：

- `eval/report/eval_cases.csv`：逐条明细，含**判定（拒答/含糊/作答）**、要点是否命中、引用、耗时、回答摘录；
- `eval/report/eval_report.md`：汇总表 + **需要人工看的用例清单**（负例被作答、正例拒答、含糊、要点缺失），
  每条都写了"为什么需要你看"；
- `--summary-json`：同一份汇总的机器可读版本，给门禁用（人看报告和机器卡门禁必须是同一组数字）。

## 六、回归门禁：把"看着还行"换成退出码

改动前跑一次、写基线，改动后跑一次、和基线比：

```bash
# 基线（仓库内提交，团队共同基准）
python -m eval.offline --chunks chunks.jsonl --cases eval/cases/enterprise_policy.json \
  --summary-json eval/baseline/offline.json

# 改动后
python -m eval.offline --chunks chunks.jsonl --cases eval/cases/enterprise_policy.json \
  --summary-json eval/report/offline.json
python -m eval.regression --baseline eval/baseline/offline.json --current eval/report/offline.json
```

门槛按指标方向分别设（`eval/regression.py:GATES`）：

| 方向 | 指标 | 门槛 |
|---|---|---|
| 越低越差 | 命中率 / 检索命中率 / 引用命中率 / 拒答率(负例) / 召回率@k / MRR | 允许下降 5 个百分点 |
| 越高越差 | 误拒率 / 含糊率 | 允许上升 5 个百分点 |
| 越长越差 | 延迟 P50 / P95 | 允许到基线的 1.5 / 2 倍 |

退化 → 退出码 1。门禁只拦"不可接受的退化"，不拦小样本噪声：天天报警的门禁等于没有门禁。
确认是改进后，用 `--update` 覆盖基线并**提交到仓库**，让基线变更留下记录。

共享 CI 机器上延迟波动大，按倍数阈值会误报，所以 CI 里用 `--ignore` 跳过延迟指标，
只卡正确性：

```bash
python -m eval.regression --baseline ... --current ... \
  --ignore 本地检索P50_ms,本地检索P95_ms
```

## 七、badcase 回流：让评测集长大

上线时手写的 12 条用例，三个月后还是 12 条，而用户的问题早换了一轮。
`eval/badcase.py` 把"反馈 → 用例"的路径固定下来：

```
反馈（CSV/JSONL） → 统一字段 → 按问题去重 → 候选用例（JSON）
   → 复核表（Markdown，给人看） → 人工补 must_include / 标负例 → --merge 并入用例集
```

**机器只做整理，不做判断**。一句"答错了"背后可能是：用户问法不规范、模型没答好、
文档里根本没写。自动转成用例，等于把三种噪声一起写进回归门禁，门禁很快就没人信了。
所以合并门槛是硬的：

| 情况 | 能否入集 |
|---|---|
| 负例（`unanswerable: true`） | 可以直接入集 |
| 正例且填了 `must_include` | 可以入集 |
| 正例但没填要点 | **拒绝**，并说明"没写考点的用例进了门禁也判不出口径" |
| 与已有用例重复（去空白/大小写后） | 跳过，复核表里标注 |
| 原因写"太慢/卡顿" | 只提示登记为性能问题，不建议入集 |

```bash
# 1) 生成候选与复核表（不动种子用例集）
python -m eval.badcase --feedback feedback.jsonl \
  --cases eval/cases/enterprise_policy.json

# 2) 人工编辑 eval/cases/field_candidates.json，补 must_include / 标负例

# 3) 合并（写回后立刻按评测口径再校验一遍）
python -m eval.badcase --feedback feedback.jsonl \
  --cases eval/cases/enterprise_policy.json --merge
```

## 八、已知不足

- 用例是脱敏等价问法，覆盖不到真实问题的长尾；
- `must_include` 是关键词式判定，"答对了但用了同义词"会被误判为不命中（宁可严，但要知道这个偏差）；
- `expected_clause` 需要人工标注，冷启动只能先标高频繁问题；
- 时效类问题依赖文档元信息，当前只从正文抽取版本/生效日期，未接文档管理系统；
- chat 模式评测消耗 token，因此不进每次提交的门禁，只在发版前跑。
