# 01 · 业务场景与 POC 范围

## 场景

企业内部的"知识找人"问题很具体：

- 制度文件散落在 OA、共享盘、邮件附件里，同一份《差旅办法》有 V2.1、V3.2 两个版本；
- 员工问的是"出差 9 天谁批"，答案在《差旅办法》第 5 条的一张表里；
- 行政、财务、HR 每天重复回答同样的问题，答案还经常不一致。

POC 的目标不是做一个"什么都能答"的聊天机器人，而是验证三件事：

1. 把**制度类文档**灌进知识库后，员工的高频问题能不能被正确回答、并给出条款出处；
2. 答不出来的时候，系统**会不会瞎答**（企业场景里这是红线）；
3. 这套链路在**内网、私有化部署**下能不能稳定跑（模型、向量库、存储都不出内网）。

## 范围（做 / 不做）

| 做 | 不做 |
|---|---|
| 制度、流程、产品说明等**文本为主**的文档 | 扫描件 OCR、图纸、音视频 |
| 单库 50~200 篇、问答并发 < 20 | 全公司级知识中台、多租户计费 |
| 中文问答、条款级引用 | 多语言、跨库联邦检索 |
| 用脱敏数据做**可复算的评测** | 对外承诺准确率指标 |

## 为什么选 WeKnora 做基座

评估过三条路：

1. **自研**（解析 + 向量库 + 检索 + LLM 拼起来）：可控、轻，但企业侧要的权限、多空间、
   审计、文档管理界面都得自己补，POC 周期撑不住；
2. **开源 RAG 框架 + 自研业务层**（本方案）：解析、混合检索、问答与界面直接用现成的，
   把精力放在**文档质量、评测、稳定性**这三件真正决定效果的事上；
3. **云厂商托管知识库**：开箱即用，但数据出内网，制度类文档不能接受。

WeKnora 是 MIT 协议、Go 实现、支持私有化部署（模型、向量库、存储可替换），
并且对外提供完整的 REST API——这决定了它可以被当成"基座"而不是"黑盒产品"。

## 交付物与验收

| 交付物 | 验收方式 |
|---|---|
| 清洗与分块规则 | `pipeline.ingest --dry-run` 能打印每块的层级路径与字符数，人工抽查 20 块 |
| 评测体系 | 固定用例集 + 一条命令产出 CSV/Markdown 报告，两次改动之间可比 |
| 客户端与异常治理 | 超时/重试/限流/熔断有单测；空召回、积压、延迟有自检脚本 |
| 部署编排 | `deploy/` 一份 compose，模型与向量库地址全部走环境变量 |

## 边界说明

- 企业真实文档不出内网，本仓库只保留**结构等价的脱敏样例**；
- 评测用例是等价改写，用于**回归对比**，不能当作对外准确率承诺；
- 本文档描述的是 POC 范围内的结论，不代表生产可用。
