# 02 · 文档清洗与分块规范

> 这一层的质量决定了整个 RAG 的上限。检索、重排、大模型都只能"用好"已经切好的块，
> 切错了，后面所有环节都在为一个错误的输入做优化。

## 一、清洗：去掉什么、留下什么

| 内容 | 处理 | 原因 |
|---|---|---|
| 页眉页脚（"内部资料""第 X 页 共 Y 页"） | 删除 | 会被当成正文召回，挤掉真正有用的条款 |
| 裸页码（"- 3 -"） | 删除 | 同上 |
| 目录行（"第一章 总则 ……… 1"） | 删除 | 目录和高价值条款字面高度相似，抢排名 |
| 每页重复的文档标题 | 只保留第一次 | 重复标题会让"标题相似度"类检索失真 |
| 文件编号 / 版本号 / 生效日期 / 失效日期 / 发布部门 | **抽出成元信息块，放在正文最前** | "哪一版""什么时候生效"恰恰是高频问题，也是版本治理的输入 |
| 密级 / 适用范围 | **抽出成元信息** | 决定这块内容能不能进某个人的上下文（见 `pipeline/security.py`） |
| 编制 / 审核 / 批准签署栏 | 删除 | 对问答没有信息量 |
| 全角数字、全角字母、全角空格、零宽字符 | 归一为半角 / 删除 | 否则"第５条"和"第5条"是两个词 |
| "第 三 条" 这类编号断裂 | 合并为"第三条" | 编号是分块和引用的锚点，断了就切不准 |

### 1.1 为什么不用整段 NFKC

最省事的写法是 `unicodedata.normalize("NFKC", text)`，一行搞定全角归一。但它会顺手把
**中文全角标点**改成英文半角：

```
第1条，应当：报销（含税）；金额≤200元
第1条,应当:报销(含税);金额≤200元
```

标点虽然大多不进分词，但代价是真实的：

- 引用给用户看的是原文，标点变了像"二手转述"，核对时对不上；
- 和原文做逐字比对（审计、条款核对）时，差异全部变成噪声；
- 目录行识别原本靠 NFKC 把"……"折成"..."才能匹配，归一化规则一改就漏（本仓库真的踩过这个坑）。

所以只折"看起来一样、编码不同"的字符：全角数字、全角字母、全角空格。
中文标点原样保留，标题/目录的匹配规则自己写清楚（`_TOC_LINE` 显式支持 `...`、`···`、`……` 三种省略号）。

## 二、分块：为什么不是"每 500 字切一刀"

### 2.1 层级路径注入

每个块的正文前加一行路径：

```
【第二章 出差审批 › 第5条】
审批权限如下：
| 天数 | 审批人 | 是否需要分管副总审批 |
...
```

好处：短块也带上下文。像"1-3 天 主管 否"这种只有一行的块，
如果没有路径前缀，向量里几乎没有可检索的语义。

### 2.2 条款边界优先

顺序是：**条款边界 → 句子 → 硬切**。宁可块短，不要一条半。
反例：把"第 4 条 审批权限"和"第 5 条 报销流程"切进同一块，
检索"谁审批"时会把报销流程一起召回，答案里混入无关条款。

### 2.3 表格整表不切

表格一旦被切断，任何一段都没有完整含义：

```
| 4-7 天 | 部门负责人 | 否 |     ← 只剩这一行，天数和审批人都还在，但表头丢了
```

所以含表格的块**允许超过大小上限**，并在元数据里标 `oversized=true` 便于追踪。
代价是块大小不均，召回时排序可能偏向表格块——用重排或块权重缓解决，
但先保证"表格是完整的"。

### 2.4 短块合并

一条制度常常只有一句话（"本办法自发布之日起施行。"），单独成块信息太薄。
同章相邻、合并后不超上限、且不含表格的块会合并，减少碎块噪声。

**合并必须把被并块的条款号写回正文**。两个块合一块之后，块头路径只剩第一个条款号，
后面那条的内容就"没有出处"了：用户问"第10条怎么规定"时，这一块既召回不回来
（路径里没有第10条），引用也会指错（指成第9条）。所以合并时补一行 `第10条 正文…`，
四个字换条款级引用不串号。

### 2.5 稳定块 ID（uid）

`uid = sha1(doc_id + 层级路径 + 正文)[:12]`。内容没变 uid 不变，改两个字 uid 就变。
没有它，跨批次对比只能靠 `(doc_id, index)` 对齐——前面某块长度一变，后面全部错位，
"这条答案出自哪一版"就永远说不清。台账（`pipeline/ledger.py`）记的就是 uid 列表。

### 2.6 参数与默认值

| 参数 | 默认 | 调整依据 |
|---|---|---|
| `max_chars` | 600 | 中文制度文档一个条款 + 表格通常在 200~500 字；600 能容纳一条完整条款及其表格 |
| `overlap` | 80 | 只在超长段落被切开时补上下文；条款边界切分不需要大重叠 |
| `min_chars`（合并阈值） | 120 | 低于此值的块优先参与合并 |

### 2.7 表格：整表入块之外，再走一条结构化旁路

整表入块保证"看得见"，但不保证"算得对"。"出差 9 天谁审批"需要把 9 和
"8 天及以上"做一次区间比较；"二线城市普通员工住 5 晚报多少"需要一次乘法。
让语言模型读表做这件事，错一次就是一次报销事故。

所以表格同时走两条路：

| 路径 | 产物 | 用途 |
|---|---|---|
| 检索路径 | 整张表进一个块 | 语义问答、解释"审批权限怎么规定" |
| 结构化路径 | 表头/行 + 条款路径的 JSON | 数值题做确定性查询（等值/区间/包含） |

```bash
python -m pipeline.tables --dir data/sample --query "出差天数=9"
# [企业差旅与费用管理办法.md · 第二章 出差审批 › 第5条] 出差天数=8 天及以上，审批人=部门负责人 + 分管副总，...
```

区间解析支持 `1-3 天`、`8 天及以上`、`3 天以内`、`500 元/晚` 等常见写法；
入库时加 `--tables-out data/tables.json` 会随批次一起导出，供问答服务做数值旁路。

边界：只处理 Markdown 表格；合并单元格、多行表头、跨页续表不猜，给 warning 并跳过；
查询不做聚合和跨表 join。

### 2.8 旧块清理：文档变短之后，旧块不会自己消失

`chunks` 模式的标题是"文档名#003"。文档删掉一条或改短之后，重新入库只会补新块，
旧块仍留在库里——检索时照常召回，答案里出现"已经删掉的规定"，比答错更难查。

台账里的 `chunks_detail`（uid + 序号 + 条款路径）正好可以用来对齐：

| 情况 | 判定 | 处理 |
|---|---|---|
| uid 还在新块里 | unchanged | 不用动 |
| 同序号但 uid 变了 | changed | 内容改了，标题会重复；先删旧标题再重传 |
| 序号超出新块数，或 uid 不在新块里 | removed | 删除该知识条目 |

```bash
python -m pipeline.prune --dir data/sample --ledger data/ledger/ingest.jsonl
```

**只出计划，不删数据**：POC 不确认上游删除接口的幂等语义，
"清理脚本删错数据"比"旧块多召回一次"严重得多，删除必须在管理端或明确接口上执行。
非 `chunks` 模式的标题由上游解析器决定，清单只能参考。

## 三、入库的三种模式（入库内容必须等于评测内容）

原样上传文件时，本地的清洗与分块只作用于离线评测，线上是 WeKnora 自己的解析器在切。
**评测报告再漂亮，也证明不了线上**——这是 POC 最容易自欺的地方。

| 模式 | 上传什么 | 适用 | 代价 |
|---|---|---|---|
| `cleaned`（默认） | 清洗后的整篇 Markdown | 常规制度库：清洗规则真正生效，上游仍按自己的规则切 | 分块仍以上游为准 |
| `chunks` | 每块一个小文件（`文档名#003.md`） | 需要条款级引用、需要块级回溯 | 知识条目数 ×8~10，旧块不自动清理 |
| `raw` | 原文件 | 保留上游解析能力（docx/pdf 版式） | 清洗与分块规则不生效 |

清洗稿与切块落在 `data/staging/`（gitignore），上传前落盘的理由：
失败能重跑、能人工打开看一眼、能用 sha256 判断"这一版到底传没传过"。
状态键里带 `mode`——同一份源文件用不同模式产出的知识条目不同，不能因为"源文件没变"就跳过。

加 `--policies-out data/policies.json` 还会落一份**策略清单**（文档 → 密级/适用范围），
给检索层按角色过滤用：线上返回的块里没有密级字段，只能靠清单反查。

## 四、怎么验证分块是对的

1. `python -m pipeline.ingest --dir data/sample --dry-run --dump chunks.jsonl`
2. 抽查：随机 20 块，看三件事——**层级路径对不对、表格完不完整、有没有一条半**；
3. 反向验证：拿 5 个已知问题，在块里 grep 必答要点，找不到就说明清洗洗过头了；
4. 结构体检：`python -m pipeline.quality --dir data/sample`，看有没有"无标题块/裸短块"。

## 五、已知不足

- 只处理 Markdown/纯文本；docx/pdf 交给 WeKnora 的解析器，两边规则不一致时以谁为准需要约定；
- 表格只做整表保留，没做结构抽取（"二线城市普通员工住 5 晚能报多少"这类计算题仍会答错）；
- 附录、附件编号与正文条款的关联没有建模；
- 数值行防护（"1.5 倍""3.5 天"不当标题）是黑名单式判断，遇到没收录的单位词仍可能误判，
  需要 dry-run 抽查。
