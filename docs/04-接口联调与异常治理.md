# 04 · 接口联调与异常治理

## 一、联调阶段最常见的五类问题

| 现象 | 根因（按概率） | 处理 |
|---|---|---|
| 401 / 403 | Token 没带、Scope 不含该知识库 | 先 `GET /knowledge-bases` 确认可见范围，再查 Token 权限 |
| 404 | 知识库/知识条目 ID 对不上（复制粘贴串号） | 用列表接口打印真实 ID 再比对 |
| 上传成功但检索不到 | 解析未完成 / 解析失败 / 分块为空 | `ops.doctor` 看解析状态；查文件是否加密、是否扫描件 |
| 检索结果为空 | 分块被清洗洗掉；或者用词与文档完全不同 | 先拿原文片段直接 grep 块文件，确认内容还在 |
| 偶发 502 / 超时 | 网关、模型服务抖动、并发过高 | 客户端重试 + 限流；再看上游是否在重启 |

## 二、客户端的四道保护

代码在 `client/weknora.py`，每一条都有单测（`tests/test_client.py`）。

### 1. 超时

连接 5s、读 30s。**没有超时的客户端事故，比任何 bug 都难排查**：
线程池被挂死之后，表现是"服务还在，但所有请求都卡住"。

### 2. 重试 + 指数退避 + 抖动

- 只重试：超时、连接失败、429、5xx；
- 不重试：400/401/403/404——参数写错重试三遍还是错，只是浪费时间掩盖问题；
- 退避：0.5s → 1s → 2s，加 0~30% 随机抖动。**抖动是必须的**：一批客户端同时重试，
  会把刚恢复的上游再打挂一次。

### 3. 限流

令牌桶，默认 5 QPS，入库与评测共用一个桶。入库是长任务，限流既保护上游，
也让"进度"变得可预期。

### 4. 熔断

连续 5 次可重试失败后打开 30 秒。期间直接返回 `CircuitOpenError`，不再打上游。
好处是把"故障放大"变成"快速失败"，让调用方有机会降级（返回"知识库暂时不可用，请稍后再试"）。

### 5. 幂等（针对入库）

文件入库前算 sha256，与本地状态文件比对，内容没变就不重复上传。
重跑流水线、断点续传、失败重试都不会产生重复知识条目——
这类"重复数据"在线上极难清理。

## 三、错误分类与对外话术

```python
RetryableError   # 超时/429/5xx → "知识库服务繁忙，请稍后重试"
FatalError       # 4xx        → "请求参数有误 / 无权限"，日志里带状态码与响应体前 300 字
CircuitOpenError # 熔断中      → "知识库暂时不可用"
```

**不要把所有异常都包成"服务异常"**：用户看到的话术可以统一，但日志里必须能区分
"我们错了"和"上游错了"，否则排查永远从零开始。

## 四、上线自检（ops/doctor.py）

```
[1/5] 连通性 OK，23 ms
[2/5] 知识库 3 个，目标库可见
[3/5] 知识条目 86 条，解析中 2 条
[4/5] 空召回 0/3
[5/5] 检索延迟 P50 180 ms / 最大 420 ms
```

退出码：0 通过、1 硬失败（连不上 / 全部空召回）、2 仅告警（积压、延迟偏高）。

设计原则：**从下往上查**。连不上就不查分块，全部空召回就不看单条回答的质量。

## 五、日志与可观测

- 每次请求记录：路径、状态码、耗时、重试次数（`client.last_retry_count`）；
- 评测与入库记录批次 ID，方便把"这个答案不对"回溯到"哪一批文档、哪次入库"；
- 不记录文档正文与用户问题原文到公共日志（制度文档涉密，问题里也可能带个人信息）。

## 六、已知不足

- 熔断是进程内的，多实例部署时各熔各的，需要的时候要换成共享状态（Redis）；
- 没有接入指标系统（Prometheus），当前靠自检脚本与日志；
- SSE 流式问答的断流重连没有覆盖，POC 内用同步接口。
